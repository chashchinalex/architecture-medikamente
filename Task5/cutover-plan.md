
# Cutover-план по миграции системы Medikamente 

## 1. Исходная ситуация и целевая модель

### Текущее состояние
- Монолит на Windows Server 2022  
- 1С Бухгалтерия и 1С Торговля в файловом режиме  
- Документы и рабочие файлы хранятся на файловом сервере  
- ККМ взаимодействуют через OLE  
- 35 сотрудников, один офис  

### Планируемая архитектура
- Микросервисная структура  
- PostgreSQL с шифрованием  
- API Gateway, IAM, RBAC/ABAC  
- Порталы для клиентов и ресепшена  
- Интеграция с лабораторией  

### Ограничения
- Недопустимость простоя  
- Защита PHI  
- Малочисленный IT‑отдел  
- Планируемое расширение сети

## 2. Подход к миграции

### Сравнение стратегий

| Параметр | High-Level Design | Parallel Run | Branch by Abstraction |
|---------|-------------------|--------------|------------------------|
| Сложность | высокая | средняя | высокая |
| Риск простоя | высокий | низкий | средний |
| Сроки | короткие | длительные | средние |
| Требования | высокие | умеренные | высокие |
| Откат | сложный | простой | средний |
| Стоимость | низкая | высокая | средняя |

**Выбор:** *Parallel Run*.

**Причины:**
- сохранение непрерывности работы клиники  
- возможность сравнивать данные в обоих системах  
- адаптация команды без давления  
- минимальные риски при откате

## 3. Cutover-план

| Этап | Содержание | Ответственные |
|------|------------|---------------|
| 0.1 | Аудит данных | Аналитик |
| 0.2 | Очистка данных | Аналитик + подразделения |
| 0.3 | Инфраструктура | Техдиректор + DevOps |
| 0.4 | ETL и синхронизация | DevOps + разработчик |
| 0.5 | Обучение IT | Подрядчик |

### Фаза 1. Перенос данных (1 неделя)

| Этап | Содержание |
|------|------------|
| 1.1 | Полный бэкап |
| 1.2 | Перенос справочников |
| 1.3 | Миграция мастер‑данных |
| 1.4 | Миграция транзакций |
| 1.5 | Проверка полноты |

### Фаза 2. Параллельная работа (4 недели)

| Этап | Содержание |
|------|------------|
| 2.1 | Новая система в режиме чтения |
| 2.2 | Пилотная группа |
| 2.3 | Расширение группы |
| 2.4 | Полный переход |
| 2.5 | Постоянная синхронизация |

### Фаза 3. Стабилизация (2 недели)

- Мониторинг производительности  
- Сбор отзывов  
- Исправление ошибок  
- Оптимизация процессов  

### Фаза 4. Отключение старой системы (1 неделя)

- Финальная проверка  
- Завершение ETL  
- Архивация предыдущей системы  
- Подготовка документации  
- Закрытие проекта  

---

## 4. План отката

### Основания для отката
- Потеря данных  
- Недоступность новой системы  
- Большой процент жалоб сотрудников  
- Инциденты безопасности  

### Процедура
1. Решение об откате  
2. Уведомление пользователей  
3. Переключение на прежнюю систему  
4. Синхронизация изменений  
5. Проверка  
6. Анализ причин  

Максимальное время отката — **до 4 часов**.
